# 嵌入式项目工作流快速启动

## 1. 最轻量的使用方法

新项目不需要重新配置一整套工作流。采用下面的最小组合即可：

```text
复制一份最小 AGENTS.md
          ↓
发送一次项目接管提示词
          ↓
以后每个阶段只说目标和禁区
          ↓
主 AI 实现与测试，独立 AI 审查，工程师硬件验收
```

第一次接管项目通常只需要几分钟。AI 负责从仓库中查找大部分软件信息；工程师只确认 AI 无法可靠推断的硬件事实和安全边界。

## 2. 新项目只做两步

### 第一步：复制最小规则

打开[嵌入式项目 AGENTS.md 最小模板](./嵌入式项目AGENTS最小模板.md)，把其中的模板代码块复制到新项目根目录，保存为：

```text
AGENTS.md
```

第一次使用时可以保留“待确认”，不必先填写完整。不要为了配置 Agent 而阅读整个工程；下一步让 Agent 自己进行只读摸底。

### 第二步：发送项目接管提示词

复制下面的提示词：

```text
这是我第一次让你接手这个嵌入式项目。

请遵守根目录 AGENTS.md，先只读分析，不要修改文件，
不要烧录固件，也不要操作真实硬件。

请自行阅读与项目有关的：
- README 和 docs
- 构建脚本、工程配置和 CI 配置
- 程序入口、任务、中断和回调
- 驱动、协议、缓存、存储、网络和控制模块
- 已有测试、日志和故障记录

输出：
1. 用通俗语言说明系统目标和主要数据流；
2. 列出关键文件、任务、中断、队列和缓冲区；
3. 找出有依据的构建、测试和烧录方法；
4. 区分已确认事实、设计假设、未知项和资料冲突；
5. 列出最可能推翻方案的高风险未知项及验证方法；
6. 提出 AGENTS.md“项目专属信息”的补充建议，并注明依据；
7. 建议一个范围最小、容易验证的第一个开发阶段。

没有依据的信息写“未知”，不要自行补全。
```

收到结果后，你通常只需要检查和补充：

- 实际使用的硬件与板卡版本；
- 正确的构建、烧录和测试命令；
- 明确不能修改的模块；
- 性能、内存和实时性硬指标；
- 电机、继电器及现场设备的安全边界；
- 真实硬件怎样验收。

这些内容确认后，再允许 AI 更新 `AGENTS.md`。项目接管到此完成，不需要配置 MCP、Skill、Plugin、Hook 或 Automation。

## 3. 日常开发只用一句话

对于边界明确、风险较低的本地软件任务，使用“轻量模式”：

```text
请按 AGENTS.md 执行。

本阶段目标：[一句话说明目标]
禁止修改：[关键禁区；没有额外禁区时写“按 AGENTS.md”]

先只读定位并复述目标、范围和验收方法。
如果修改局部、安全、可回退且没有阻塞性未知项，直接完成最小改动并运行相关测试。
如果涉及架构取舍、硬件参数、扩大范围、删除数据、外部写入或真实设备，停在计划阶段等我确认。

完成后报告修改文件、实际测试结果、未验证项和硬件验收建议。
```

例如：

```text
请按 AGENTS.md 执行。

本阶段目标：修复流式解析器收到半帧后无法继续解析的问题。
禁止修改：drivers/、motor/ 和芯片配置。

先只读定位。如果属于局部、安全、可回退的修改，直接实现并运行协议单元测试；
否则停在计划阶段。完成后报告改动、测试和未验证项。
```

这类任务不要求你提前写完整设计。Agent 应从仓库中找出相关文件和测试，并在既定边界内完成工作。

## 4. 什么时候必须使用“计划模式”

遇到下面任一情况，不要直接实现：

- 需要修改架构、线程模型或模块接口；
- 需要改变中断、DMA、缓存所有权或任务优先级；
- 性能、内存或实时性前提尚未验证；
- 涉及存储掉电一致性或网络异常策略；
- 涉及电机、急停、限位、限流和现场设备；
- 预计修改范围较大，或者回退困难。

计划提示词：

```text
请按 AGENTS.md 进入计划模式，先不要修改文件。

目标：[本阶段目标]
已知限制：[不能突破的限制]

请输出：
1. 当前事实、假设、未知项和资料冲突；
2. 可能推翻方案的高风险假设及最小验证实验；
3. 建议修改和禁止修改的文件；
4. 最小实现步骤；
5. 软件测试与人工硬件验收标准；
6. 回退方法。

等我确认后再执行。
```

确认计划时，不需要逐句重写。可以直接回复：

```text
计划确认。补充两点：
1. [纠正的事实或新增限制]
2. [必须满足的验收条件]

请执行当前阶段，完成后运行测试并报告未验证项。
```

## 5. 阶段完成后怎样审查

主 AI 完成后，先由工程师快速查看代码差异，确认没有明显越界修改。然后在独立 AI 会话中发送：

```text
请作为独立审查者，只审查当前阶段，不要修改文件。

请先阅读 AGENTS.md、阶段目标、验收标准、代码差异和测试结果。
不要默认现有架构和主 AI 的实现正确，也不要因为测试通过就认定没有问题。

重点检查：
- 是否满足阶段目标和验收标准
- 缓冲区边界、整数溢出和内存生命周期
- 中断、线程、数据竞争和实时性
- 错误恢复和最坏情况
- 测试是否遗漏关键失败路径
- 是否超出允许修改范围

按严重程度报告问题。
每个问题写明代码位置、触发条件、后果和验证方法。
没有充分证据的内容标记为“待验证风险”。
```

审查 AI 只负责发现问题。是否成立、是否修改以及如何完成硬件验收，仍由工程师决定。

## 6. 阶段结束时只保存必要上下文

阶段结束后，不需要写一份很长的总结。让 AI 更新项目已有的状态文档；如果项目还没有状态文档，可以使用下面的最小格式：

```md
# 项目状态

## 已完成

- [阶段目标和对应提交]

## 已验证

- [软件测试及结果]
- [硬件版本、条件和实测结果]

## 未验证与遗留风险

- [未知项、风险和验证方法]

## 下一阶段

- [一个边界明确的下一目标]
```

只有长期规则发生变化时才更新 `AGENTS.md`。阶段结果、硬件实测和下一步放在状态文档中，避免 `AGENTS.md` 越写越长。

## 7. 三种使用模式速查

| 情况 | 使用方式 | 是否等待确认 |
|---|---|---|
| 第一次打开项目 | 项目接管提示词 | 只读分析后由工程师确认事实 |
| 局部、安全、可回退的软件修改 | 轻量模式 | 无阻塞风险时可直接实现 |
| 架构、实时性、掉电、电机或大范围修改 | 计划模式 | 必须确认计划后实现 |
| 阶段实现已经完成 | 独立审查提示词 | 审查只报告，工程师决定 |

## 8. 不要过早增加配置

开始实际项目时，通常不需要：

- 为每个项目新建 Skill；
- 配置一组复杂 Hook；
- 安装与任务无关的 Plugin；
- 一开始就并行启动多个 Agent；
- 把整套工作流复制进项目文档。

当一种流程已经在多个项目中重复使用，并且手工复制确实造成负担时，再把它封装成 Skill。需要访问 GitHub、团队文档或测试数据库时再配置连接器或 MCP。需要定期无人值守检查时再考虑 Automation。

最小原则是：

> 能用一份 `AGENTS.md` 和一句任务目标解决的问题，不增加新的配置层。
