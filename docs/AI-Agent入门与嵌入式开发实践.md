# AI Agent 入门与嵌入式开发实践

## 阅读路线

如果你第一次使用 AI Agent，建议先阅读第 1～7 章并完成一次只读任务。需要连接外部服务时再读第 8 章；准备复用或自动化流程时再读第 9 章；第 10～12 章可以作为嵌入式项目实践与检查手册。

## 1. 先从一个实际任务认识 AI Agent

假设你接手了一个 STM32 数据采集工程。现场反馈“设备运行几个小时后偶尔丢帧”，工程中同时有串口 DMA、协议解析、SD 卡存储和以太网上报。

如果使用普通聊天 AI，你可能会复制一段代码过去并询问哪里有问题。它只能根据你提供的片段回答。

使用 AI Agent 时，你可以先让它在项目目录中完成一个只读任务：

```text
请阅读 README、设计文档以及串口接收、协议解析和数据存储相关代码。

请输出：
1. 数据从串口进入到写入存储的完整路径；
2. 关键任务、中断、队列和缓冲区；
3. 有文件依据的事实；
4. 尚未确认的假设、未知项和资料冲突；
5. 建议由工程师进一步确认的问题。

每项结论注明依据文件。先不要修改文件，也不要提出重构方案。
```

这里的 **AI Agent（智能代理）**，可以简单理解为“能够围绕目标读取资料、使用工具、执行多步工作并报告结果的 AI”。它不只是回答问题，还可能读取文件、搜索代码、运行构建或测试，以及在授权后修改文件。

这并不表示 Agent 可以独立决定工程目标。更可靠的关系是：

```text
工程师给出目标、边界和验收标准
              ↓
Agent 完成可检查的软件工作
              ↓
工程师审查结果并完成真实硬件验收
```

对于嵌入式项目，第一项任务应当尽量是只读分析。先观察 Agent 怎样理解项目、引用证据和表达未知项，再逐步允许它修改代码。

## 2. 完成第一个只读项目分析任务

### 2.1 打开完整项目目录

应在 Codex 中打开项目根目录，而不是只打开某一个源文件。完整目录通常包含：

- `README` 和设计文档；
- 构建脚本、工具链配置和芯片配置；
- 驱动、协议、业务逻辑和测试；
- 项目级 `AGENTS.md`；
- 已有日志和故障记录。

Agent 只有看到必要上下文，才有机会判断某个串口回调是在中断中执行，某个缓冲区由谁拥有，以及协议解析结果最终流向哪里。

### 2.2 让 Agent 用证据复述

第一次任务可以直接复制下面的提示词：

```text
请先只读分析这个项目，不要修改任何文件，也不要运行会改变外部状态的命令。

请阅读：
- README 和 docs/ 中与本任务有关的文档；
- 构建入口和主要配置；
- 程序入口、任务、中断和回调；
- 与串口接收、协议解析、缓存和存储有关的代码；
- 已有测试。

输出：
1. 项目目标和当前状态；
2. 模块职责与完整数据流；
3. 关键文件、函数、任务、中断、队列和缓冲区；
4. 当前构建与测试方法；
5. 事实、假设、未知项和资料冲突；
6. 每项重要结论的文件依据。

如果资料不足，请明确写“未知”，不要自行补全。
```

### 2.3 怎样检查分析结果

不要只看回答是否流畅。至少检查：

- 引用的文件和函数是否真实存在；
- 数据流是否漏掉 DMA、中断、队列或缓存所有权；
- 文档和代码冲突时，Agent 是否明确报告；
- 推测是否被误写成事实；
- Agent 是否遵守了“只读、不修改”的限制。

例如，代码中配置波特率为 `460800`，文档写的是 `115200`。正确的输出应是“资料冲突，需要确认实际配置”，而不是擅自选择其中一个。

## 3. 怎样把任务说清楚

一个可执行的任务至少包含四部分：目标、范围、限制和验收标准。

| 项目 | 要回答的问题 | 嵌入式示例 |
|---|---|---|
| 目标 | 这次要解决什么问题？ | 实现与 HAL 无关的流式协议解析器 |
| 范围 | 允许查看和修改什么？ | 只修改 `protocol/` 和 `tests/protocol/` |
| 限制 | 哪些行为禁止或必须确认？ | 不修改驱动、波特率、电机控制和引脚配置 |
| 验收标准 | 怎样才算完成？ | 半帧、粘包、CRC 错误和超长帧测试通过 |

可以使用下面的通用模板：

```text
任务目标：
[用一句话说明本轮要得到什么结果]

背景和已知事实：
- [事实及其来源]
- [事实及其来源]

允许范围：
- 可读取：[目录或文件]
- 可修改：[目录或文件]

限制：
- 不修改：[内容]
- 不执行：[硬件动作或外部操作]
- 遇到以下情况先暂停确认：[条件]

验收标准：
- [可检查的结果 1]
- [可检查的结果 2]
- [需要工程师完成的硬件验证]

请先复述你的理解。发现信息冲突时先报告，不要猜测。
```

“优化串口程序”不是清晰任务，因为不知道要优化吞吐量、延迟、内存还是可维护性。“修改完成后测试一下”也不是验收标准，因为没有说明测试输入和预期输出。

### 3.1 标注信息可信度

在复杂工程中，建议始终使用下面五类信息：

| 类别 | 含义 | 示例 |
|---|---|---|
| 已确认事实 | 有代码、测量或已确认资料支持 | UART3 使用 DMA 循环接收 |
| 设计假设 | 为继续设计暂时采用的判断 | SD 卡最长阻塞小于 20 ms |
| 未知项 | 当前资料无法回答 | DMA 缓冲区满后是否覆盖旧数据 |
| 资料冲突 | 不同来源给出不同结论 | 文档与代码的波特率不同 |
| 验证方法 | 怎样把未知变成事实 | 连续发包并用逻辑分析仪测量 |

这个分类能防止一条未经验证的假设逐渐变成后续设计的“默认事实”。

## 4. 让 Agent 先规划、再执行、再验证

### 4.1 为什么要分三个阶段

例如，目标是修复 UDP 接收在乱序时的异常。比较稳妥的顺序是：

```text
规划：确认数据格式、风险、修改范围和测试方法
  ↓
执行：只实现当前阶段所需的最小改动
  ↓
验证：运行测试、检查差异、报告未验证项
```

规划不是写一份很长的愿望清单，而是把即将发生的修改变得可检查。高风险未知项尚未解决时，计划中应先安排实验，而不是直接安排完整重构。

### 4.2 规划提示词

```text
请先制定本阶段计划，不要修改文件。

计划必须包含：
1. 已确认事实、设计假设、未知项和资料冲突；
2. 可能推翻方案的高风险假设；
3. 准备修改与明确不修改的文件；
4. 最小实现步骤；
5. 自动测试与人工硬件验收标准；
6. 失败时如何回退。

等我确认计划后再执行。
```

只要提示词中写了“等我确认”，Agent 就应停在规划阶段。工程师确认前不能开始修改。

### 4.3 执行提示词

```text
计划已确认，请只执行当前阶段。

- 实现最小必要改动；
- 不顺手增加下一阶段功能；
- 运行约定的构建、静态检查和自动测试；
- 不操作真实设备；
- 若必须扩大范围、删除数据或访问外部系统，先暂停并说明原因。

完成后报告修改文件、测试结果、失败项和仍需人工确认的内容。
```

### 4.4 验证结果

Agent 报告“测试通过”时，还应检查：

- 它实际运行了什么命令；
- 命令是否成功执行，而不是因为缺少工具被跳过；
- 测试是否覆盖边界和异常路径；
- 代码差异是否超出约定范围；
- 是否仍有只能在真实硬件上确认的问题。

更完整的工程流程见[嵌入式工程师使用 Codex 的分阶段开发工作流](./嵌入式工程师使用Codex的分阶段开发工作流.md)。

## 5. 使用 `AGENTS.md` 保存长期规则

假设你每次都要重复告诉 Agent：“修改 C 文件后运行单元测试；不要自动使能电机；文档使用中文。”这类对整个仓库长期有效的规则适合写入 `AGENTS.md`。

`AGENTS.md` 是 Codex 会在工作前读取的项目指导文件。根目录文件适用于整个仓库；更靠近当前工作目录的嵌套指导可以为子目录补充或覆盖更宽泛的规则。

一个适合嵌入式项目的最小示例：

```md
# 项目规则

## 构建与测试

- 修改 `protocol/` 后运行 `ctest --test-dir build`。
- 修改目标固件后运行项目规定的无硬件构建命令。
- 无法运行的测试必须明确报告，不得写成已通过。

## 代码边界

- 未经确认不要修改芯片引脚、时钟树和链接脚本。
- 不要把动态内存引入中断或实时控制路径。

## 安全

- 不得自动使能真实电机。
- 不得解除急停或提高电流、速度和 PWM 上限。
- 真实硬件动作必须由工程师确认并执行。

## 完成要求

- 报告修改文件、测试结果和未验证项。
```

适合写入 `AGENTS.md` 的内容包括：

- 稳定的构建和测试命令；
- 目录职责和编码约定；
- 每次都必须执行的检查；
- 仓库级安全规则；
- 文档与代码维护要求。

不适合写入的内容包括：

- 只对本次任务有效的临时要求；
- API Key、设备密码、访问令牌和客户数据；
- 很长的背景资料或会快速过期的状态记录。

一次性要求放在当前提示词，项目状态放在交接或状态文档，长期规则才放入 `AGENTS.md`。

## 6. Agent 怎样使用工具完成工作

“工具”是 Agent 可以调用的具体能力，例如读取文件、搜索文本、运行命令、修改文件、查看图片或访问已授权的外部服务。

以修复协议解析器为例，Agent 可能依次：

1. 搜索解析器入口和测试文件；
2. 读取相关源码；
3. 运行现有测试建立基线；
4. 修改允许范围内的文件；
5. 再次运行测试并检查差异；
6. 报告仍未覆盖的硬件行为。

工具调用通常比纯文字回答更接近真实工程工作，但工具输出也需要检查。编译成功只能证明当前构建条件下没有编译错误，不能证明串口时序、电机方向或掉电恢复正确。

### 6.1 常见权限级别

可以把权限理解为 Agent 的工作围栏：

- **只读**：可以检查资料，但不能修改文件；
- **工作区写入**：可以在当前项目内修改，访问项目外部或网络通常仍受限制；
- **更高权限**：可能访问网络、项目外目录或系统资源，需要更谨慎地授权。

**沙箱（sandbox）** 是限制文件、网络和系统访问范围的隔离环境。它的目标是把工具操作限制在任务需要的边界内。

遇到权限请求时，不要只看“允许/拒绝”，而要检查：

- 为什么必须执行这项操作；
- 命令会读取或修改什么；
- 目标路径是否明确；
- 是否会连接外部系统；
- 能否先用只读或更小范围的方法完成。

### 6.2 哪些操作应暂停确认

- 删除、覆盖或批量移动文件；
- 修改工作区以外的内容；
- 安装依赖或访问网络；
- 推送代码、创建工单、发送消息等外部写操作；
- 写入设备、烧录固件或操作真实硬件；
- 扩大原先约定的修改范围。

即使某个工具在技术上可用，也不代表 Agent 已经获得执行所有动作的业务授权。

## 7. 权限、安全和敏感信息

### 7.1 从最小权限开始

第一次让 Agent 接触项目时，优先使用只读任务。需要实现代码时，再开放工作区内必要的写权限。只有任务确实需要联网或访问外部服务时，才增加相应权限。

例如，分析本地串口驱动不需要访问互联网；查询 GitHub 上的评审意见才可能需要已授权的 GitHub 连接。

### 7.2 不要把秘密写进仓库

以下内容不得放入提示词示例、配置样例或仓库文件：

- API Key 和访问令牌；
- 私钥和设备证书私钥；
- 设备密码、量产密钥和调试后门；
- 客户现场数据及其他敏感信息。

需要认证时，应使用系统提供的凭据管理、环境变量或连接器授权机制，并确保日志不会输出秘密。

### 7.3 AI 能做、能辅助和不能替代的工作

| 类型 | 示例 |
|---|---|
| AI 可完成的软件工作 | 修改解析器、编写模拟器、运行单元测试、分析日志 |
| AI 可辅助的审查 | 检查越界、数据竞争、错误恢复、测试遗漏 |
| 必须由工程师完成 | 电气参数确认、示波器测量、抓包、掉电、长稳和真实电机验收 |

## 8. MCP：连接外部工具和资料

假设故障描述在 GitHub Issue，协议说明在团队文档系统，测试数据在数据库中。仅打开本地仓库时，Agent 看不到这些内容。

**MCP（Model Context Protocol，模型上下文协议）** 是连接 Agent 与外部工具或上下文的一种标准方式。通俗地说，它像一套统一插座，让 Agent 在授权范围内读取外部资料或调用外部动作。

MCP 服务可以提供：

- 工具：例如查询工单、读取日志或执行数据库查询；
- 资源：例如文档、接口说明和知识库内容；
- 提示模板：例如团队统一的故障分析格式。

适合使用 MCP 的场景：

- 读取 GitHub Issue 或 Pull Request；
- 查询团队文档和设计稿；
- 读取测试数据库中的非敏感数据；
- 调用内部诊断服务。

不需要 MCP 的场景：

- 文件已经在本地仓库中；
- 只需搜索或修改当前项目代码；
- 可以用更简单的本地命令安全完成。

连接外部系统时先确认：

1. 是只读还是允许写入；
2. 能访问哪些仓库、空间或数据表；
3. 是否会接触客户数据或生产系统；
4. 写操作是否需要逐次确认；
5. 凭据是否由安全的授权机制保存。

例如，读取 GitHub 评审意见和“直接合并 PR”是两种不同权限。前者不应自动扩展为后者。

## 9. Skills、Plugins、Connectors、Hooks、Automations 和多 Agent

这些能力放在基础协作流程之后学习。初学者不需要先配置完整工具链，才能完成第一个项目分析或代码修改任务。

### 9.1 Skill：可重复使用的工作方法

**Skill（技能）** 是一套可重复使用的任务说明，可以附带脚本、参考资料和模板。

例如，把下面的流程做成“嵌入式协议审查”Skill：

```text
读取协议与实现
→ 检查帧边界、长度和 CRC
→ 检查半帧、粘包和重新同步
→ 运行规定测试
→ 按统一格式报告问题
```

当团队反复执行同一种审查或发布流程时，Skill 比每次重新编写长提示词更合适。

### 9.2 Plugin：可安装、可分享的能力包

**Plugin（插件）** 是可安装和分享的能力包。它可以组合 Skills、连接器、MCP 工具、Hook 或其他资源。

选择方法很简单：

- 只需要一套可复用的任务步骤：优先考虑 Skill；
- 需要把工作流、外部连接和工具一起安装或分发：考虑 Plugin；
- 已经有成熟插件满足需求：先评估权限和适用范围，再决定是否安装。

### 9.3 Connector：已授权的应用连接

**Connector（连接器）** 可以理解为与 GitHub、文档系统或协作平台等应用建立的授权连接。它让 Agent 在授权范围内访问私有工作区数据或执行应用操作。

连接器迁移到新电脑后通常需要重新安装或授权。不要把访问令牌复制到项目文件中。

### 9.4 Hook：在关键时机自动执行检查

**Hook（钩子）** 是在 Agent 生命周期的特定时机运行的检查或脚本。例如：

- 在工具执行前检查命令是否包含危险路径；
- 在提示提交时检测是否误贴 API Key；
- 在一轮工作结束时运行格式或合规检查。

Hook 属于进阶能力。它会执行代码，因此必须审查来源、脚本内容、触发条件和权限。不要把 Hook 当成真实硬件安全回路；软件 Hook 无法替代急停、限位或硬件限流。

### 9.5 Automation：按计划重复执行任务

**Automation（自动化或定时任务）** 用于按计划重复执行工作，例如每天汇总测试失败、定期检查文档链接或跟踪 Pull Request 状态。

定时任务可能无人值守运行，因此应：

- 先手动测试提示词；
- 使用尽可能小的权限；
- 优先只读检查；
- 明确何时停止、何时请求人工处理；
- 避免自动操作真实设备或生产系统。

### 9.6 多 Agent：把独立角色分开

**多 Agent** 是把任务交给多个相互独立或分工明确的 Agent。最实用的入门方式不是同时生成大量代码，而是把“实现”和“审查”分开：

```text
主 AI：按已确认范围实现并测试
  ↓
独立审查 AI：只审查，不默认实现正确
  ↓
工程师：判断问题、决定修改并完成硬件验收
```

独立会话能减少沿用主 AI 推理假设的可能，但它仍然可能出错，不能成为最终责任主体。

## 10. 嵌入式项目的完整分阶段实战

下面用一个机器人数据采集与电机控制系统贯穿整个流程：

```text
传感器/编码器
   ├── 串口或 RS-485
   └── 以太网
          ↓
     嵌入式控制器
     ├── 数据采集
     ├── 协议解析
     ├── 数据缓存和存储
     ├── 状态监控
     └── 电机控制
          ↓
     上位机或机器人平台
```

### 阶段 0：验证高风险假设

在决定架构前先验证：

- 串口峰值流量下 DMA 是否丢数据；
- SD 卡最坏写入延迟是否会堵塞采集；
- UDP 丢包、重复和乱序如何影响上层；
- 控制任务的真实周期和抖动；
- 电机方向与限位逻辑是否符合实际接线。

AI 可以编写 PC 发包器、UDP 模拟器和数据分析脚本。逻辑分析仪测量、实际 SD 卡掉电测试和电机方向确认必须由工程师执行。

### 阶段 1：实现独立协议解析器

范围只包含协议解析及其 PC 单元测试，不修改驱动和电机控制。

验收示例：

- 支持半帧、连续帧和粘包；
- CRC 错误不输出有效数据；
- 超长长度不会越界；
- 错误后能够重新同步；
- 不使用动态内存；
- 单元测试全部通过。

### 阶段 2：接入串口 DMA 与环形缓冲区

重点检查中断与任务之间的数据所有权、读写索引原子性、缓冲区覆盖策略和峰值吞吐量。

软件测试可以模拟写指针回绕和突发数据；真实 DMA 行为及串口时序需要逻辑分析仪验证。

### 阶段 3：加入缓存与存储

先根据实测最坏写入延迟确定队列深度，再定义：

- 数据积压时的背压或丢弃策略；
- 空间不足和文件损坏时的行为；
- 掉电后允许丢失多少数据；
- 数据恢复和索引重建方式。

### 阶段 4：实现网络模拟和上报

AI 可以编写 UDP 设备模拟器，构造丢包、重复、乱序、断网和突发流量。工程师使用抓包工具确认真实网络行为。

### 阶段 5：审查电机控制状态机

先在仿真环境检查：

- 通信超时是否进入安全状态；
- 编码器异常是否被检测；
- 限流、限速和限位是否始终有效；
- 急停解除后是否仍需人工重新使能；
- 故障恢复是否可能产生意外运动。

主 AI 完成每个阶段后运行软件测试，工程师检查差异并建立可回退检查点，再由独立 AI 审查。确认的问题修复并回归后，最后由工程师执行真实硬件验收。

## 11. 串口、网络、存储和电机安全检查

### 11.1 串口与 RS-485

- [ ] 波特率、校验位和帧格式已经由工程师确认
- [ ] 半帧、粘包、错误帧和超长帧已经测试
- [ ] DMA 缓冲区回绕和覆盖行为已经确认
- [ ] 中断与任务之间没有未经保护的数据竞争
- [ ] 峰值流量和长稳测试已经在真实硬件上执行

### 11.2 以太网

- [ ] 断网、重连、丢包、重复和乱序已经测试
- [ ] 突发流量不会造成无界队列增长
- [ ] 超时、重试和降级策略已经明确
- [ ] 抓包结果与软件日志能够对应
- [ ] 外部输入的长度和内容已经校验

### 11.3 数据存储

- [ ] 最坏写入延迟来自实测而非标称速度
- [ ] 空间不足、写入失败和文件损坏有明确处理
- [ ] 掉电一致性和允许丢失范围已经定义
- [ ] 日志不会保存密钥或客户敏感数据
- [ ] 恢复后不会把损坏数据误当成有效数据

### 11.4 电机与现场设备

- [ ] AI 没有自动使能真实电机
- [ ] AI 没有解除急停或故障状态
- [ ] AI 没有提高电流、速度或 PWM 上限
- [ ] 限位、看门狗和通信超时保护没有被绕过
- [ ] 急停解除后不会自动恢复运动
- [ ] 测试已使用硬件限流、低速和安全负载条件
- [ ] 所有真实动作由工程师确认并执行

AI 可以生成测试方案、仿真代码和检查清单，但不能替代现场安全责任人。

## 12. 常见问题与一页速查表

### 12.1 常见问题

**Agent 给出了很完整的方案，可以直接实现吗？**

不能仅凭表达完整就执行。先检查事实依据，把假设和未知项分开，并优先验证可能推翻架构的风险。

**每次修改一个文件都要确认吗？**

阶段范围和验收标准已经明确时，可以授权 Agent 完成范围内的安全本地修改和测试。扩大范围、删除数据、访问外部系统或操作真实硬件时应暂停确认。

**自动测试都通过了，是否可以交付？**

不可以。自动测试属于软件验证，不能替代串口时序、网络抓包、存储掉电、长稳和真实电机测试。

**审查 AI 发现的问题都必须修改吗？**

不一定。审查结论是待工程师判断的输入。应结合代码、触发条件和硬件约束确认问题是否成立。

**什么时候应该使用 MCP？**

当任务所需资料或动作位于本地仓库之外，并且有合适的授权边界时使用。仅处理本地文件时通常不需要。

**Skill 和 Plugin 有什么区别？**

Skill 偏向一套可复用的工作步骤；Plugin 是可安装、可分享的能力包，可以组合 Skill、外部连接和其他工具。

**是否应该一开始就配置 Hook、Automation 和多 Agent？**

不需要。先掌握只读分析、任务边界、结果检查和分阶段实现，再为确实重复或需要隔离的工作增加这些能力。

### 12.2 任务开始前速查

- [ ] 目标是否具体？
- [ ] 允许和禁止的范围是否明确？
- [ ] 验收标准是否能实际检查？
- [ ] 事实、假设、未知项和资料冲突是否分开？
- [ ] 是否先验证了可能推翻方案的高风险假设？
- [ ] 是否明确禁止未经确认的真实硬件动作？

### 12.3 Agent 完成后速查

- [ ] 是否只修改了约定范围？
- [ ] 构建、静态检查和自动测试是否真实运行？
- [ ] 边界条件和失败路径是否覆盖？
- [ ] 工程师是否检查了代码差异？
- [ ] 是否建立了可回退的代码检查点？
- [ ] 独立 AI 是否完成只读审查？
- [ ] 已确认问题是否修复并回归？
- [ ] 哪些项目仍需真实硬件验证？
- [ ] 文档是否记录了验证结果和遗留风险？

### 12.4 最小可复制提示词

```text
请先复述任务目标、允许范围、禁止事项和验收标准。

开始前区分：
- 已确认事实
- 设计假设
- 未知项
- 资料冲突

只完成当前阶段的最小必要改动，并运行约定的软件测试。
不要操作真实硬件，不要扩大修改范围；遇到删除、外部写入或高风险操作时先暂停确认。

完成后报告：
1. 修改的文件及原因；
2. 实际运行的测试及结果；
3. 未运行或失败的检查；
4. 仍需工程师完成的硬件验收；
5. 已知限制和遗留风险。
```

## 13. 推荐学习顺序与延伸阅读

建议按下面的顺序练习：

1. 在一个熟悉的项目中完成只读分析；
2. 用目标、范围、限制和验收标准描述一个小任务；
3. 让 Agent 分阶段修改并运行本地测试；
4. 学会检查代码差异和验证报告；
5. 用 `AGENTS.md` 固化长期规则；
6. 再按实际需要引入 MCP、Skills、Plugins、Hooks、Automations 和多 Agent。
