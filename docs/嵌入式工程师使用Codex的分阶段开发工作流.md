# 嵌入式工程师使用 Codex 的分阶段开发工作流

## 1. 这套工作流适合什么项目

这套流程适合使用 Codex 辅助开发以下系统：

- 串口、RS-485、CAN 和以太网数据采集
- 协议解析、数据缓存与本地存储
- STM32、RTOS 或嵌入式 Linux 软件
- 编码器采集、机器人电机状态机与控制程序
- 需要经过台架、现场或真实硬件验收的项目

它的目标不是让 AI 一次生成整个系统，而是让 AI 在工程师控制下完成：

```text
理解项目 → 发现风险 → 设计架构 → 分阶段实现
         → 独立审查 → 真实验收 → 记录结果
```

工程师始终负责需求取舍、硬件参数、安全边界和最终验收。AI 负责加快资料梳理、设计分析、代码实现、软件测试和代码审查。

---

## 2. 对原有五步流程的评价

原流程是：

1. 让 AI 阅读资料并复述理解。
2. 分析当前设计的缺陷和系统瓶颈。
3. 给出可调整的架构，并按风险优先原则划分阶段。
4. 按阶段进行设计和实现。
5. 另开一个 AI 辅助验收，然后提交代码。

整体方向正确，尤其值得保留的是：先理解、风险优先、小步实现和独立复核。

但需要补充四点：

1. **理解资料后不能立即认定资料正确。** 必须区分事实、推测、未知项和资料冲突。
2. **架构设计前先验证高风险假设。** 例如测量 SD 卡最差写入延迟，而不是只根据标称速度设计队列。
3. **每个阶段开始前定义验收标准。** 不能等代码完成后再决定怎样算通过。
4. **不要等全部验收完成后才第一次提交。** 应先形成可回退的代码检查点，再进行独立审查和硬件验收；验收通过后再记录最终结果或打标签。

独立 AI 能辅助软件验收，但不能替代示波器、逻辑分析仪、抓包、长稳测试、掉电测试和真实电机安全测试。

---

## 3. 推荐的完整工作流

### 第 0 步：建立任务基线

先由工程师说明项目目标和不可突破的边界。

至少提供：

- 目标硬件、操作系统和工具链
- 本阶段要解决的问题
- 性能、内存、实时性和协议约束
- 允许修改的目录
- 禁止修改或必须人工确认的内容
- 最终验收条件

示例提示词：

```text
这是一个 STM32 + FreeRTOS 的机器人采集与控制项目。

本轮目标是重构 RS-485 数据接收和协议解析，不修改电机控制逻辑。
禁止改变波特率、设备协议和硬件引脚配置。
不允许自动使能真实电机。

请先阅读资料和代码，不要修改文件，也不要立即设计方案。
```

建议把长期约束写入项目根目录的 `AGENTS.md`，例如构建命令、测试命令、目录职责、禁止操作和电机安全要求。一次性要求留在当前提示词中。

### 第 1 步：AI 阅读资料并复述理解

让 Codex 阅读：

- `README`、`docs` 和协议文档
- 原理图或硬件接口说明
- 构建脚本和配置文件
- 程序入口、线程、任务和中断
- 驱动、协议、存储和控制模块
- 已有测试、日志和故障记录

要求输出：

1. 系统目标和当前状态
2. 模块职责和数据流
3. 关键线程、中断、队列和缓冲区
4. 已有构建和测试方法
5. 资料与代码不一致的地方

推荐提示词：

```text
请阅读项目资料和相关代码，复述你对系统的理解。

输出系统结构、主要数据流、关键文件和函数。
请给每项结论注明依据来自哪个文件。
先不要提出重构方案，也不要修改代码。
```

工程师在进入下一步前应纠正 AI 的误解。没有确认的内容不能成为架构前提。

### 第 2 步：建立“事实—假设—未知项”清单

这是资料阅读与系统设计之间最重要的过渡步骤。

| 类别 | 示例 |
|---|---|
| 已确认事实 | UART3 使用 DMA 接收，缓冲区为 512 字节 |
| 当前假设 | 最坏情况下存储写入不会阻塞超过 20 ms |
| 未知项 | DMA 缓冲区满时是否会覆盖旧数据 |
| 资料冲突 | 文档写 115200，代码配置为 460800 |
| 验证方法 | 用逻辑分析仪和连续发包程序测量 |

提示词：

```text
请不要把推测当成事实。

把当前结论整理为：
1. 有代码或资料依据的事实
2. 为了继续分析而做出的假设
3. 尚未确认的问题
4. 资料之间的冲突
5. 每个关键未知项的验证方法
```

关键未知项如果可能推翻架构，就必须先验证。

### 第 3 步：分析缺陷、瓶颈和系统风险

不要只让 AI 罗列代码问题，要从完整数据链路分析：

```text
硬件接收 → 驱动缓冲区 → 协议解析 → 消息队列
        → 数据处理 → 本地存储/网络上报/电机控制
```

重点检查：

- 峰值吞吐量和最坏延迟
- 缓冲区是否可能覆盖或越界
- 队列积压时的背压和丢弃策略
- 中断与线程之间的数据竞争
- 优先级反转和控制周期抖动
- 存储变慢、断网、掉电时的行为
- 故障能否隔离，系统能否恢复
- 电机通信超时、编码器异常和急停后的状态

要求 AI 按“证据、触发条件、影响、严重程度、验证方法”报告问题。没有证据的判断应标注为待验证风险。

### 第 4 步：先做风险实验，再确定最终架构

先验证最可能推翻方案的问题，而不是先实现最简单的模块。

常见的阶段 0 实验包括：

- 测量串口峰值流量下的 DMA 行为
- 构造半帧、粘包、乱码和 CRC 错误
- 测量 SD 卡最差写入延迟和掉电结果
- 模拟 UDP 丢包、乱序、重复和突发流量
- 测量控制任务的实际周期和抖动
- 在断开负载、限流和限速条件下确认电机方向

这些实验可以使用临时代码或 PC 模拟器，目的只是验证假设，不要求直接进入产品代码。

完成实验后再让 AI 调整架构：

```text
请结合已确认事实和风险实验结果给出最小可行架构。

说明：
- 每个模块存在的必要性
- 模块接口和数据所有权
- 线程、中断、队列及缓冲区关系
- 错误处理和降级策略
- 内存、吞吐量和时间预算
- 被放弃的方案及原因

不要为未经确认的未来需求增加复杂抽象。
```

重要取舍建议写成简短的架构决策记录（ADR），防止后续 AI 不知道为什么采用当前设计。

### 第 5 步：按风险和依赖关系划分阶段

每个阶段都应能独立实现、验证和回退。一个阶段必须明确：

- 阶段目标
- 输入和输出
- 允许修改的文件
- 不允许修改的内容
- 依赖条件
- 自动化测试
- 硬件验收方法
- 完成标准

示例：

```text
阶段目标：实现与 HAL 无关的流式协议解析器。

允许修改：protocol/ 和 tests/protocol/。
禁止修改：drivers/、motor/ 和硬件配置。

通过条件：
- 支持半帧、连续多帧和粘包
- CRC 错误不输出有效数据
- 超长数据不会造成越界
- 错误帧后能重新同步
- 不使用动态内存
- PC 单元测试全部通过
```

推荐顺序不是固定的，应优先安排高风险、高不确定性或会影响后续接口的阶段。

### 第 6 步：主 AI 实现当前阶段

一个会话只聚焦当前阶段，不要让它顺手实现后续功能。

执行顺序：

1. 主 AI 复述阶段目标和限制。
2. 查看相关代码及测试。
3. 给出本阶段的小计划。
4. 实现最小必要改动。
5. 编译并运行静态检查、单元测试和模拟测试。
6. 报告改动文件、测试结果和未验证内容。
7. 工程师检查差异。

阶段边界已明确时，可以让 AI 直接完成安全的本地修改和自动测试，不必对每个小文件重复确认。涉及扩展范围、外部写入、删除数据或真实硬件动作时必须暂停确认。

### 第 7 步：建立代码检查点

软件测试通过且工程师检查差异后，建立一个可回退的 Git 提交。这个提交表示“当前实现可供审查”，不表示硬件已经验收通过。

推荐区分：

```text
代码检查点：形成可回退的 Git commit
软件验收：编译、静态检查和自动测试通过
硬件验收：台架、长稳或现场测试通过
```

如果希望提交历史只保留最终结果，可以在独立审查和硬件验收完成后再整理提交；但验收前仍应保留一个安全、可恢复的版本检查点。

### 第 8 步：使用独立 AI 会话审查

建议另开一个 Codex 会话，让它只做审查，不直接修复。新会话不会沿用主 AI 的完整推理过程，更容易质疑原设计中的假设。

给审查 AI 提供：

- 阶段目标和验收标准
- 架构说明或 ADR
- 本阶段代码差异
- 自动测试结果
- 已知限制和未验证项

审查提示词：

```text
请作为独立审查者检查本阶段代码。
不要默认现有设计正确，也不要因为测试通过就认定没有问题。

重点检查：
- 是否满足阶段验收标准
- 缓冲区边界和整数溢出
- 中断、线程和数据竞争
- 错误恢复和最坏情况
- 实时性、内存和资源释放
- 测试是否遗漏关键异常路径
- 是否修改了阶段范围之外的内容

先按严重程度报告问题，不要修改代码。
每个问题注明代码位置、触发条件、后果和建议验证方法。
```

审查 AI 的结论仍需工程师判断。确认的问题交回主 AI 修复，再重新执行测试和审查。

### 第 9 步：工程师完成真实验收

根据模块选择验收方法：

- 串口：逻辑分析仪、错误帧、峰值流量和长稳测试
- 以太网：抓包、断网、突发流量、丢包和乱序测试
- 存储：掉电、空间不足、文件损坏和写入积压测试
- 电机：硬件限流、低速空载、方向、通信超时、急停和故障复位测试

电机测试必须保留人工安全关口：

- AI 不得自动使能真实电机
- 不得自动解除急停或故障
- 不得自行提高电流、速度或 PWM 上限
- 急停解除后不得自动恢复运动
- 所有真实运动步骤由工程师确认并执行

验收失败时，应记录“实际现象、复现步骤、日志或波形、预期结果”，再让 AI 分析，不要只说“测试失败了”。

### 第 10 步：完成阶段并更新文档

阶段通过后：

1. 修正审查和硬件验收发现的问题。
2. 再次运行回归测试。
3. 整理或补充 Git 提交。
4. 记录硬件、固件版本和验收结果。
5. 更新架构文档和项目状态。
6. 明确遗留风险后再开始下一阶段。

建议长期维护：

- `AGENTS.md`：项目规则、命令、验证要求和安全边界
- `docs/ARCHITECTURE.md`：当前真实架构、接口和数据流
- `docs/PROJECT_STATUS.md`：已完成、已验证、未验证和下一阶段
- `docs/adr/`：重要架构取舍及其原因
- `docs/validation/`：硬件版本、测试条件和验收记录

## 4. Codex Sol 的使用分工

Sol 是模型，轻度和中度是推理强度。比较实用的分工如下：

| 工作 | 建议强度 |
|---|---|
| 阅读资料、定位代码、整理文件 | 轻度 |
| 明确接口下的局部实现 | 轻度 |
| 编写测试、模拟器和日志工具 | 轻度 |
| 梳理完整数据流和系统瓶颈 | 中度 |
| 架构设计、风险排序和阶段划分 | 中度 |
| 并发、实时性和复杂故障分析 | 中度 |
| 独立代码审查和电机安全状态机审查 | 中度 |

推荐节奏：

```text
中度：理解系统、分析风险和设计架构
  ↓
轻度：完成边界明确的阶段实现和常规测试
  ↓
中度：独立审查、复杂故障分析和阶段复盘
```

不要仅凭感觉选择推理强度。可以记录不同任务在轻度和中度下的正确率、返工次数、耗时和遗漏问题，逐渐形成自己的选择规则。

OpenAI 当前把 GPT-5.6 Sol 定位为复杂专业工作和编程的旗舰模型，并建议以中度作为平衡起点、以轻度处理更重视速度的工作。模型和产品能力会变化，使用时应参考最新的 [GPT-5.6 Sol 模型说明](https://developers.openai.com/api/docs/models/gpt-5.6-sol) 和 [模型使用指南](https://developers.openai.com/api/docs/guides/latest-model)。

## 5. 每个阶段的快速检查表

开始阶段前：

- [ ] AI 已复述目标和限制
- [ ] 事实、假设和未知项已经分开
- [ ] 高风险假设已经验证或明确记录
- [ ] 修改范围已经限定
- [ ] 软件与硬件验收标准已经确定
- [ ] 电机和现场设备的安全边界已经明确

实现完成后：

- [ ] 工程能够编译
- [ ] 静态检查和自动测试通过
- [ ] 异常路径和边界条件已测试
- [ ] 工程师已检查代码差异
- [ ] 已建立可回退的代码检查点
- [ ] 独立 AI 已完成审查
- [ ] 已确认的问题已经修复并回归
- [ ] 真实硬件验收已经完成
- [ ] 架构、状态和验收文档已经更新

## 6. 最终推荐流程

```text
工程师定义目标与安全边界
          ↓
AI 阅读资料并复述理解
          ↓
事实、假设、未知项和冲突清单
          ↓
分析系统缺陷、瓶颈和风险
          ↓
用小实验优先验证高风险假设
          ↓
确定最小架构和阶段验收标准
          ↓
主 AI 实现当前阶段并运行自动测试
          ↓
工程师检查差异并建立代码检查点
          ↓
独立 AI 会话审查
          ↓
修复问题并重新测试
          ↓
工程师完成真实硬件验收
          ↓
整理提交、更新文档、进入下一阶段
```

最值得坚持的原则是：

> 先确认理解，再分析问题；先验证风险，再确定架构；先定义验收，再开始实现；AI 负责辅助审查，工程师负责真实系统的最终判断。
