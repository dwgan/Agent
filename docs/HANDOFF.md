# 项目交接说明

更新时间：2026-08-05

## 1. 项目目标

编写一套面向 AI Agent 初学者的中文指导资料。

目标读者主要是嵌入式开发工程师，日常工作涉及：

- 现场串口、RS-485、CAN 和以太网数据采集
- 通信协议解析、缓存和数据存储
- STM32、RTOS 或嵌入式 Linux 软件开发
- 机器人编码器、电机状态机和控制程序
- 软件测试、台架验证和现场故障排查

文档应让读者先学会怎样与 Agent 合作，再逐步理解 `AGENTS.md`、工具、MCP、Skills、Plugins、Hooks、Automations 等功能。

`template/.agents/skills/README.md` 用于说明项目级 Skills 的用途。除了模板自带的提交 Skill，新项目不需要立即创建更多 Skill；只有稳定重复的流程才应继续封装。

模板现已包含 `commit-worktree` Skill。调用后，它会检查当前 Git 工作目录的范围、差异、敏感信息和项目验证，生成合适的提交说明并创建本地提交。它默认不执行 push、amend 或跳过 Git hooks；遇到范围外的既有暂存、冲突状态、疑似秘密或测试失败时会停止并报告。

2026-08-04 已补充提交信息规则。Codex 官方没有强制统一的 commit message 语法，官方原则是把团队工程规范和 PR 期望写入 `AGENTS.md`，并在提交前测试和审查差异。因此模板先服从用户要求、项目规范和近期提交历史；没有可用约定时，才回退到 Conventional Commits 的 `<type>(<scope>): <description>` 格式。破坏性变更必须标记，复杂提交可记录正文和实际测试结果。

同日针对 IAR 生成的 CRLF 工程文件补充了换行处理：`template/.gitattributes` 使用 `* text=auto` 自动识别文本并在 Git 仓库中规范化为 LF；工作区仍可由开发工具使用 LF 或 CRLF。`commit-worktree` 的空白检查显式启用 `cr-at-eol`，因此不会把 CRLF 中的 `CR` 误报为行尾空白，但仍会阻止真正的尾随空格、Tab 和空白文件尾。模板禁止为了换行检查批量重写无关文件。

`progress-review` Skill 固定俯视总结的输出格式：当前阶段目标、已完成、正在解决的问题、关键决策及物理/协议原因（标注依据或推断）、事实/假设/未知、待工程师确认点、下一步。`observer` 是只读讲解角色，适合工程师需要独立第二视角时按需调用，成本高于 Skill。该机制只读、不碰硬件；真实项目中的效果仍待试用验证。

## 3. 已确认的推荐工作流

完整流程是：

```text
工程师定义目标与安全边界
          ↓
AI 阅读资料并复述理解
          ↓
建立事实、假设、未知项和资料冲突清单
          ↓
分析系统缺陷、瓶颈和风险
          ↓
用小实验优先验证高风险假设
          ↓
确定最小可行架构和阶段验收标准
          ↓
主 AI 实现当前阶段并运行自动测试
          ↓
工程师检查代码差异并建立可回退检查点
          ↓
使用独立 AI 会话审查
          ↓
修复问题并重新测试
          ↓
工程师完成真实硬件验收
          ↓
整理提交、更新文档、进入下一阶段
```

需要长期坚持的原则：

1. 资料中的内容不自动等于事实。
2. 不把 AI 的推测写成已确认结论。
3. 先验证可能推翻架构的高风险假设。
4. 开始实现前就确定验收标准。
5. 一个阶段只处理边界明确的一组工作。
6. 软件测试后先建立可回退的代码检查点。
7. 独立 AI 负责辅助复核，不负责最终硬件验收。
8. 串口时序、网络行为、存储掉电和电机安全必须由工程师实测。

## 4. 主 AI、审查 AI 与工程师的分工

### 主 AI

- 阅读资料并复述系统理解
- 分析代码、数据流和系统风险
- 提供架构候选方案
- 按确认的阶段范围实现代码
- 运行编译、静态检查和自动测试
- 报告修改内容和未验证项目

### 独立审查 AI

- 不默认主 AI 的架构和实现正确
- 对照阶段目标和验收标准审查代码差异
- 检查边界、并发、实时性和异常恢复
- 检查测试是否遗漏关键失败路径
- 先报告问题，不直接修改代码

### 工程师

- 决定需求、架构取舍和安全边界
- 确认硬件型号、电气参数和现场条件
- 判断 AI 报告的问题是否成立
- 检查代码差异并决定是否提交
- 完成台架、长稳、掉电和真实设备验收
- 对最终系统行为和安全负责

## 5. Codex Sol 的使用习惯

用户日常主要使用 Codex 的 Sol 模型，并在轻度和中度推理之间切换。

建议分工：

| 任务 | 推理强度 |
|---|---|
| 阅读资料、搜索文件、定位函数 | 轻度 |
| 已确定接口下的局部实现 | 轻度 |
| 编写常规测试、模拟器和日志工具 | 轻度 |
| 梳理完整数据流和系统瓶颈 | 中度 |
| 架构设计、风险排序和阶段划分 | 中度 |
| 并发、实时性和复杂故障分析 | 中度 |
| 独立代码审查和电机安全审查 | 中度 |

推荐使用节奏：

```text
中度：系统理解、风险分析和架构设计
  ↓
轻度：边界明确的阶段实现和常规测试
  ↓
中度：独立审查、复杂故障分析和阶段复盘
```

## 6. 电机与现场设备的安全边界

后续文档必须明确：

- 不允许 AI 自动使能真实电机。
- 不允许 AI 自动解除急停或故障状态。
- 不允许 AI 自行提高电流、速度或 PWM 上限。
- 不允许 AI 绕过限位、看门狗和通信超时保护。
- 急停解除后不能自动恢复运动。
- 真实动作必须由工程师确认并在安全测试条件下执行。
- AI 可以生成测试方案、仿真代码和检查清单，但不能替代现场安全责任人。

## 7. 下一步建议

下一项工作是在一个真实或示例嵌入式项目中试用 `template/`，重点检查：

1. 复制模板后，仅填写项目概况是否就能由 `architect` 完成项目摸底。
2. 项目接管结果是否能准确区分事实、假设、未知项和资料冲突。
3. `coder` 是否严格遵守已确认的文件范围和验收标准。
4. `reviewer` 是否保持独立、只报告问题且不直接修改代码。
5. 复杂或高风险任务是否能正确停在工程师确认点。
6. 模板规则是否仍有可以删除的重复内容。
7. `$commit-worktree` 是否能在不混入范围外文件的情况下完成本地提交。

复核通过后，可选择下一阶段：

- 根据真实项目反馈精简启动包；或
- 当启动流程已稳定重复使用时，再封装为 Codex Skill。

2026-08-05 已把"进度俯视与讲解"机制加入 `template/`：`progress-review` Skill 和 `observer` Agent（详见 2.8）。下一步是在真实工程中试用：先只加三条 `AGENTS.md` 规则（阶段结束先输出俯视总结、关键决策解释物理原因并标注依据、git 提交建立检查点），仍跟不上时再调用 Skill 或 Agent，并对比成本与效果。
