# 项目 AI 协作规则

本文件用于约束在本仓库中工作的主 AI 和子 Agent。复制到新项目后，请先把所有“待填写”项替换为真实信息；无法确认的内容保留为未知项，不要猜测。

## 项目概况

- 项目目标：待填写
- 目标硬件与芯片：待填写
- 构建入口：待填写
- 自动测试入口：待填写
- 主要文档：待填写
- 当前开发阶段：待填写

如果仓库包含多个工程或历史版本，不要仅凭目录名推断它们之间的关系。先通过工程文件、README、构建脚本、Git 历史或工程师说明确认目标工程和参考工程。

## 开始任务前

1. 阅读根目录说明、当前任务相关文档和代码。
2. 检查 Git 状态，区分任务开始前已有修改与本次修改。
3. 复述目标、目标工程、参考工程、禁止修改范围和验收标准。
4. 分开记录已确认事实、设计假设、未知项和资料冲突。
5. 复杂、跨模块或涉及硬件风险的任务先给出计划，等工程师确认后再实现。

信息不足但不影响安全和总体方向时，可采用明确标注的最小假设继续；如果不同选择会改变架构、硬件行为或修改范围，必须暂停并询问工程师。

## 推荐的角色协作顺序

主 AI 负责协调上下文和最终汇总。需要多角色协作时，按任务风险选择角色，不要求每个小改动都启动全部角色。

```text
architect：只读分析，给出事实、风险、方案和阶段验收标准
    ↓ 工程师确认方案与边界
coder：只在确认范围内实现，并运行安全的本地构建或测试
    ↓ 工程师检查差异并建立可回退检查点
reviewer：只读独立审查，先报告问题，不直接修改
    ↓ coder 按确认的问题修复并重新测试
工程师：完成真实硬件、台架和现场验收
```

- `architect` 适用于架构设计、复杂故障分析、跨模块修改和高风险假设验证。
- `coder` 适用于边界明确的实现、测试、构建修复和文档同步。
- `reviewer` 适用于独立代码审查、测试缺口检查，以及并发、实时性、存储和安全复核。
- `observer` 适用于工程师需要理解当前进度和关键决策原因时，只读讲解，不修改文件。
- 小型、低风险、边界清楚的修改可由主 AI 直接完成，不必机械地调用所有角色。
- 并行角色不得修改同一组文件；存在依赖关系的工作应顺序执行。

## 实现规则

- 修改前先定义本阶段的文件范围和验收标准。
- 优先做最小、可验证、可回退的修改，不顺手重构无关代码。
- 保留用户已有修改；发现重叠或冲突时先说明。
- 遵循现有代码风格、目录结构、命名和构建系统。
- 遵循 `.gitattributes` 的换行规则；不要仅为统一 CRLF/LF 重写整个文件或整个仓库。
- 不把资料描述、注释或 AI 推断自动当作硬件事实。
- 架构设计前优先验证可能推翻方案的高风险假设。
- 不在仓库中保存 API Key、访问令牌、设备密码、私钥或客户敏感数据。

## 构建与测试

- 优先运行与修改直接相关的最小测试，再运行项目已有的更完整检查。
- 不伪造编译、静态检查、单元测试或硬件测试结果。
- 报告实际执行的命令、结果，以及因环境或硬件限制而未执行的项目。
- 软件测试通过不等于硬件验收通过。

## Git 提交规则

- 用户要求提交或保存当前进度时，使用项目级 `$commit-worktree` Skill。
- 提交信息依次服从：用户明确要求、项目贡献规范或 `AGENTS.md`、近期稳定的提交风格；都不存在时使用 Conventional Commits 格式。
- 默认标题格式为 `<type>(<scope>): <description>`；`scope` 不明确时省略，不要编造。
- `feat` 表示新增功能，`fix` 表示修复缺陷；常用扩展类型包括 `docs`、`test`、`refactor`、`perf`、`build`、`ci`、`style` 和 `chore`。
- 破坏兼容性的修改必须使用 `!` 或 `BREAKING CHANGE:` 标记。
- 一个提交只表达一个主要目的；复杂提交可增加正文和 `Tests:`，但只能记录实际运行过的验证。
- 空白检查必须将 CRLF 中的 `CR` 视为合法行尾，但仍检查真正位于行尾的空格和 Tab。
- 默认只创建本地提交，不自动 push、amend 或跳过 Git hooks。

## 嵌入式与硬件安全边界

- 未经工程师明确确认，不烧录固件、不连接或控制现场设备。
- 不自动使能真实电机、解除急停或故障状态。
- 不自行提高电流、速度、功率、PWM、温度或压力上限。
- 不绕过限位、互锁、看门狗、通信超时和故障保护。
- 不执行可能擦除 Flash、EEPROM、eMMC、文件系统或设备配置的操作。
- 示波器、逻辑分析仪、抓包、掉电、长稳、EMC 和真实负载测试必须由工程师执行或现场确认。

## 完成任务时

- 汇总新增和修改的文件。
- 说明编译、测试和静态检查结果。
- 区分已经验证的结论、仍待人工确认的假设和真实硬件验收项。
- 明确遗留风险和建议的下一步。
